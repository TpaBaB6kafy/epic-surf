# Home V2 workflow

## Purpose

Home V2 is a hidden test version of the future Epic Surf School homepage. It lets the team review the new surf-zine / editorial poster-collage direction without changing the production homepages.

Перед любыми Home V2 visual changes обязательно прочитать `docs/design-experiments/home-v2/style-system/README.md`. Этот документ является главным visual authority для формы, композиции и presentation layer экспериментальных routes.

## Branch

- Active branch: `design/home-v2-poster-collage`.
- Keep Home V2 work in this branch until the experiment is approved.
- Do not merge this branch into `main` while `/home-v2` and `/ru/home-v2` are still test routes.
- Do not replace production routes `/` or `/ru` before approval.

Use the exact preview domain generated by Vercel for the latest commit in this branch.

## Noindex and sitemap rules

- `/home-v2` and `/ru/home-v2` must be accessible by direct link for review.
- Both routes must remain `noindex, nofollow`.
- Keep route-level metadata in:
  - `app/(en)/home-v2/page.js`
  - `app/(ru)/ru/home-v2/page.js`
- Both route files must keep `robots.index = false`, `robots.follow = false`, and matching `googleBot` settings.
- Do not add `/home-v2` or `/ru/home-v2` to `app/sitemap.js`.
- Do not add Home V2 routes to public header/footer navigation or SEO link sets.

## Responsive contract

This contract applies only to `/home-v2` and `/ru/home-v2`. It does not change the production routes `/` and `/ru`.

The shared visual profile is a full-width poster collage built around deep teal `#395962` and coral `#FE746A`. EN and RU must receive equivalent responsive support. Do not replace the editorial composition with generic bento UI, narrow every section into a single `max-width` container, or introduce round pill buttons.

### Classify before implementing

Every element must be assigned one responsive role before its layout rules are changed:

1. part of a proportional poster stage;
2. adaptive/mobile content;
3. conventional interface or control;
4. decorative texture, seam, or overlay.

Do not apply one responsive model to every element on the page. In particular, a full-width composition must not be constrained merely because readable prose or conventional controls elsewhere use a bounded content measure.

### Proportional poster stages

Use a proportional stage for a unified desktop composition such as the current Hero and How It Works implementations. A stage may use `aspect-ratio`, `container-type: inline-size`, `cqw`, and coordinates derived from its base Figma frame.

All stage-bound elements must scale together:

- artwork and images;
- frames, borders, textures, and decorative elements;
- headings and labels;
- card titles;
- card body copy when the copy is visually embedded in the card.

Stage geometry and type coefficients must be derived from the base composition rather than tuned arbitrarily. Stage-bound text may use a readability floor while retaining proportional growth:

```css
font-size: max(<minimum in rem>, <proportional size in cqw>);
```

The `rem` value protects readability near the stage breakpoint. Do not add a fixed upper `rem` ceiling when it would break synchronous scaling during Chrome zoom-out, and do not leave card text fixed while its card grows proportionally.

The approved How It Works desktop stage is the reference implementation:

```css
/* Card title */
font-size: max(1.1875rem, 1.326cqw);

/* Card body */
font-size: max(.75rem, .833cqw);
```

These coefficients belong to the geometry of How It Works and must not become global tokens.

### Adaptive and mobile reflow

When a proportional desktop composition no longer fits cleanly, replace it with an independent adaptive layout. Use grid or flex, change column count or order where necessary, and return content to a stable vertical flow. Mobile is not a uniformly reduced desktop poster.

Stable `rem` type sizes are appropriate after a composition stops scaling as one stage. The reflow must preserve readable EN and RU copy without overlap, clipping, horizontal overflow, or distorted proportions.

### Conventional responsive UI

Header, navigation, floating Messenger, Live Cam controls, Forecast, FAQ, Footer, CTA, and other controls remain conventional responsive UI. Implement them with grid/flex, `rem`, and bounded `clamp()` values where useful; do not turn them into proportional poster stages.

Every interactive target must be at least `44px × 44px`, with visible keyboard focus and usable touch behavior. Poster styling does not waive control ergonomics or accessibility requirements.

### Decorative layer

Textures, seams, transitions, and SVG/raster overlays belong to the decorative layer. They must follow the geometry of the section they decorate, must not create horizontal overflow, and must not be used to hide broken layout behavior.

### Section classification

Proportional or hybrid sections:

- Hero — complete;
- How It Works — complete;
- Choose Your Lesson;
- Everything Included;
- Rentals;
- Reviews;
- Events;
- Epic Moments/Gallery.

Conventional sections and controls:

- Header;
- floating Messenger;
- Live Cam and Forecast controls;
- FAQ;
- Footer.

Decorative elements:

- textures;
- seams and section transitions;
- SVG and raster overlays.

### Breakpoint ownership

Breakpoints belong to individual sections, not to the page as a whole. The current `1440px` boundary for How It Works is a section-specific decision and is not a global Home V2 breakpoint.

Choose a section breakpoint at the point where its composition can no longer fit without overlap, clipping, unreadable text, horizontal overflow, or unnatural changes in proportion. Verify every boundary at breakpoint minus `1px`, the breakpoint itself, and breakpoint plus `1px`. The transition must not introduce an unexplained visual jump or collapsed section height.

### Browser zoom contract

For every proportional stage, test real Chrome browser zoom at:

- `50%`;
- `75%` or `80%`;
- `100%`;
- `125%`;
- `200%`.

At zoom-out, text, imagery, cards, and decorations must retain their intended visual ratios. At zoom-in, a section may switch to its adaptive layout if the resulting reflow remains correct. Inspect the rendered composition as well as computed CSS; viewport emulation alone is not a complete substitute for browser zoom testing.

### QA matrix

At minimum, verify widths `390`, `640`, `768`, `899`, `900`, `1023`, `1024`, `1280`, `1366`, `1439`, `1440`, `1920`, and `2560` pixels for both EN and RU.

At every relevant width and zoom level, check:

- no horizontal overflow;
- no clipping or overlap;
- synchronous scaling of stage-bound elements;
- readable text in both locales;
- correct seams between neighboring sections;
- working CTA and controls;
- visible keyboard focus and minimum touch targets.

Never mask a local overflow defect with global `overflow-x: hidden` or `overflow-x: clip`. Fix the element or section that owns the overflow.

### Targeted implementation order

Each item is a separate targeted pass. Do not use one pass to rewrite the whole page.

1. Hero video — complete.
2. How It Works responsive, breakpoint, readability and zoom behavior — complete.
3. Responsive Poster Stage Contract in `workflow.md` — complete.
4. Choose Your Lesson + Everything Included.
5. Rentals.
6. Live Cam + Forecast.
7. Reviews + FAQ.
8. Events.
9. Epic Moments/Gallery.
10. Header + Footer + floating Messenger + inter-section transitions/seams + removal of obsolete media rules.

## Commit and push cycle

1. Make focused changes in the Home V2 branch.
2. Verify the affected local routes, especially `/home-v2` and `/ru/home-v2`.
3. For Home V2 routing, SEO, or UI changes, run the relevant checks when practical:

```bash
npm run lint
npx playwright test tests/home-v2.spec.js
```

4. Commit with a clear message that names the Home V2 area changed.
5. Push `design/home-v2-poster-collage`.
6. Open the Vercel Preview domain and manually check `/home-v2` and `/ru/home-v2`.
7. Confirm the preview root `/` still behaves as expected for the branch and remember it is not the Home V2 review URL.

## Final replacement plan

After Home V2 is approved:

1. Move the approved Home V2 experience onto `/` and `/ru`.
2. Preserve existing booking, rental, messenger, analytics, partner attribution, language switching, canonical, and structured data behavior.
3. Update canonical and language alternate metadata for the production homepages if route ownership changes.
4. Remove or retire the temporary `/home-v2` and `/ru/home-v2` routes, or keep them only if there is a documented post-launch reason.
5. If temporary routes remain after launch, keep them out of the sitemap and decide whether they should redirect to `/` and `/ru`.
6. Update `app/sitemap.js` only for approved production routes, never for abandoned experiment URLs.
7. Run production checks for `/`, `/ru`, sitemap, robots, analytics events, booking modal, rental modal, messenger links, and mobile layout.
8. Merge to `main` only after approval and verification.
